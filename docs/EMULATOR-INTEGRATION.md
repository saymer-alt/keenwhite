# Подключение Keenetic Emulator к KeenWhite (контракт `keenetic-emulator/v0`)

**Статус:** контракт-заглушка реализована (`internal/emulator`); настоящий
эмулятор (QEMU-проект «Ported 5.1.8») ещё не готов — KeenWhite к нему
подготовлен, но не вмешивается в его разработку.

## 1. Конвейер

```
GitHub Actions → Keenetic Emulator (QEMU) → keenetic-emulator/v0 → KeenWhite Harness → PASS/FAIL
```

Разметка источника результата обязательна: `LOCAL_FAKE` (сейчас),
`QEMU_USER` (сборка/smoke), `KEENETIC_EMULATOR` (будущее), `PHYSICAL`
(только после аппаратной приёмки). Результат уровня ниже никогда не
выдаётся за уровень выше.

## 2. Контракт (`internal/emulator`, `keenetic-emulator/v0`)

| Операция | Смысл | Заглушка сегодня |
|---|---|---|
| `DetectEnvironment` | модель, версия KeeneticOS, архитектура (arm64/mipsle) | `ErrUnsupported`, `emulator_kind: none` |
| `CheckCapabilities` | инвентарь 12 возможностей (OS, CPU, RAM, /opt, OPKG, сети, loopback, exec, PID, изолированные TCP/UDP, тестовый DNS) | все `UNSUPPORTED` |
| `ReadResources` | живой снимок RAM/disk | `ErrUnsupported` |
| `StageArtifact` | копия бинарника в устройство с проверкой размера+hash | `ErrUnsupported` |
| `RunIsolatedTest` | запуск ВНУТРИ устройства под жёстким таймаутом в изолированной сети | `ErrUnsupported` — никогда ничего не исполняет |
| `CollectDiagnostics` | секрето-свободный бандл | честный JSON «unsupported» |
| `Cleanup` | завершение всех детей + удаление staged | идемпотентный no-op |

Fail-closed: всё, что не `SUPPORTED` явно, трактуется как непригодное;
`UNKNOWN` — для ещё не доказанной изоляции сети.

## 3. Требования безопасности к будущей реализации

- Полная изоляция от домашней/рабочей сети; **заявлять изоляцию подтверждённой
  запрещено до реального испытания конкретной QEMU-конфигурации**.
- Никаких реальных аккаунтов VK/MAX, настоящих TURN-credentials, обращений
  к боевым VPS; тестовый DNS; никаких изменений маршрутов/DNS/firewall хоста.
- Жёсткий таймаут на каждый запуск; `Cleanup` завершает все дочерние
  процессы и удаляет staged-артефакты; идемпотентность после сбоев.
- Диагностика и отчёты без секретов (канареечные тесты — как в харнессе).
- Запуск транспортных бинарников — только через `RunIsolatedTest` внутри
  устройства, никогда на хосте.

## 4. Как будет подключаться (план, не реализация)

1. Реализовать `emulator.Environment` поверх API/CLI эмулятора (новый тип,
   например `QemuEnvironment`), не трогая сценарии харнесса.
2. В харнессе выбрать окружение по конфигурации (сегодня —
   `DefaultEnvironment()` = `LOCAL_FAKE`); отчёту добавить
   `result_source`.
3. Прогнать те же 18 сценариев + регрессии на `KEENETIC_EMULATOR`;
   публиковать отчёт отдельным артефактом с пометкой источника.
4. Физическое устройство (`PHYSICAL`) — только по отдельному owner GO
   (issue #3), вне этого контракта.

## 5. Честные ограничения

- «QEMU user-mode» (сборочные smoke) — не эмулятор Keenetic и не приёмка.
- Контракт v0 — предварительный; имена операций могут уточниться при
  появлении реального API эмулятора, при этом fail-closed семантика
  (`UNSUPPORTED`/`UNKNOWN`, изоляция только по доказательству) сохраняется.
